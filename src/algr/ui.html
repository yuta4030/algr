        algr とは

        algr は Algorithmic Development を回すためのフロー。人はルール（戦略）を書き、タスクはルールで判断を埋めたうえで、人の手に触れずにマージまで流れる。人は例外だけを受ける。

        algr 本体が持つのは、状態遷移とイベント、遷移ごとの不変条件、エージェントのプロンプトだけ。タスク管理・エージェントを動かす場所・判断の保存はアダプタの向こうに置き（いまはファイル、ローカルのプロセス、k2down）、判断はエージェントがする。本体は結果で状態を動かし、記録するだけ。

        2 つの層

        処理の層では、起票・実装・レビューのエージェントがルールを読んでタスクを流す。ルールで決まらない判断だけが人に上がる。

        人の答えを含むすべての判断は記録に残る。タスクが done になると、蒸留エージェントが人の答えと report（判断の集計）からルールの提案を出す。

        メタプログラマーが accept した提案だけがルールになり、次のタスクでは同じ論点が起票で埋まる。使うほど人に上がる判断が減っていく。

        人の立場

        人は処理の中から抜け、外側で 2 つの立場に立つ。人に聞く判断は、文脈を一番持っている起票に寄せる。

        立場やること答える判断
        クライアント何をやるか、目的、こだわり度を出す「何を大事にするか」が問われるもの
        メタプログラマー何を自動で通してよいかを決める。ルールの受け入れ、マージのゲート、公開 IF の境界を持つ「どこまで任せてよいか」が問われるもの

        それぞれの操作は下の「人の操作」にある。

        状態とイベント

        主経路は intake → ready → in-progress → review → done。

        人が関わるのは needs-decision と failed、それにマージのゲート（flow.merge = "human"）を置いたときの approved だけ。

        人が答えると必ず intake に戻り、起票エージェントがルールを当て直してから主経路に合流する。

        イベントは遷移ごとに 1 つ出て、そこに hook を差し込める。hook は既定の処理のあとに呼ばれる観察者で、遷移を止めない。遷移ごとの実績はフローで見られる。

        ルールを育てる（メタプログラミング）

        メタプログラマーは処理の中には入らず、ルールとゲートを通して何を自動で通すかを決める。

        提案を決める。蒸留エージェントは、done になったタスクの人の答えと algr distill で受けた方針から足す提案を出す。algr accept したものだけがルールになり、algr decline した提案も記録に残る。

        見直しも提案で届く。判断ごとに、従ったルール・レビューの異議・当たり外れが記録に残る。蒸留エージェントは k2down report の落とす候補（一度も当たらない）、書き直す候補（外れや異議が多い）、ぶつかる組から、外す提案と言い直しの提案も出す。メタプログラマーは report を読み込まなくても、提案を決めればよい。

        ゲートを持つ。マージのゲート（approved）、失敗からのやり直し（algr reopen）、公開 IF の境界もメタプログラマーの持ち物。

        蒸留エージェントの動き（何を読み、どの提案を出したか、失敗したか）は「いま」の蒸留の欄と、タスクの詳細で見られる。

        ルールの変更は rules.json の差分として PR に載る。そのマージを人の確認とする。
