    algr とは

    algr は Algorithmic Development を回すためのフロー。人はルール（戦略）を書き、タスクはルールで判断を埋めたうえで、人の手に触れずにマージまで流れる。人は例外だけを受ける。

    algr 本体が持つのは、状態遷移とイベント、遷移ごとの不変条件、エージェントのプロンプトだけ。タスク管理・エージェントを動かす場所・判断の保存はアダプタの向こうに置き（いまはファイル、ローカルのプロセス、k2down）、判断はエージェントがする。本体は結果で状態を動かし、記録するだけ。

    2 つの層

    処理の層では、起票・実装・レビューのエージェントがルールを読んでタスクを流す。ルールで決まらない判断だけが、聞いた役の判断待ちでクライアントに渡る。

    クライアントの答えを含むすべての判断は記録に残る。タスクが done になると、蒸留エージェントがクライアントの答えと report（判断の集計）からルールの提案を出す。

    メタプログラマーが accept した提案だけがルールになり、次のタスクでは同じ論点がルールで埋まる。使うほどクライアントに渡る判断が減っていく。

    立場

    処理の外側に 2 つの立場がある。処理の層の問いにはクライアントが、メタの層（ルール）にはメタプログラマーが答える。立場を人が埋めるか、その横の AI が埋めるかは algr は区別しない。

    立場やること答える判断
    クライアントやりたいことをまとめ、タスクに分けて順番を決める。あとは判断待ちだけに答えるタスクの問いすべて（要望したものを出してよいか、マージしてよいか、公開 IF を変えてよいかも含む）
    メタプログラマータスクには答えない。クライアントの答えの記録、algr stats、report を見てルールを直すどの判断をルールに任せるか

    それぞれの操作は下の「立場の操作」にある。PR をレビュー・マージするチーム（PJ）は立場の外で、フローの外の手続きとして扱う。

    状態とイベント

    主経路は intake → ready → in-progress → review → merging → done。

    立場に渡るのは、起票・実装・レビューそれぞれの判断待ち（waiting-intake / waiting-implement / waiting-review）と failed だけ。

    答えがそろうと聞いた役の状態に戻り、その役だけが要約から走り直す。起票には戻さない。レビューが聞いたときは、答えを持ったレビューが承認か修正依頼かを決める。

    承認するとマージのアダプタに頼み、merging でマージ先に入るのを待つ。PJ の修正依頼が来たら実装に戻る。

    イベントは遷移ごとに 1 つ出て、そこに hook を差し込める。hook は既定の処理のあとに呼ばれる観察者で、遷移を止めない。遷移ごとの実績はフローで見られる。

    ルールを育てる（メタプログラミング）

    メタプログラマーは処理の中には入らず、ルールとゲートを通して何を自動で通すかを決める。

    提案を決める。蒸留エージェントは、done になったタスクの人の答えと algr distill で受けた方針から足す提案を出す。algr accept したものだけがルールになり、algr decline した提案も記録に残る。

    見直しも提案で届く。判断ごとに、従ったルール・レビューの異議・当たり外れが記録に残る。蒸留エージェントは k2down report の落とす候補（一度も当たらない）、書き直す候補（外れや異議が多い）、ぶつかる組から、外す提案と言い直しの提案も出す。メタプログラマーは report を読み込まなくても、提案を決めればよい。

    任せる範囲を決める。マージの前に止めるかもルールで決まる（最初は「マージ前に必ずクライアントに聞く」から始め、記録を見て狭める）。失敗からのやり直し（algr reopen）もメタプログラマーの持ち物。

    この層のことは、画面上の切り替えで「メタプログラマー」に入って見る。前回の見直しからの変化、ゲート、決めること（提案と根拠）、ルールの効き、蒸留エージェントの動きがまとまっている。

    ルールの変更は rules.json の差分として PR に載る。
