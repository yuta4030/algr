# フローの作り直し（v2）

2026-10-27 の議論で決めたこと。実装はこの文書を元に 3 つのまとまり（下の「進め方」）で進める。
決めたことを実装したら、ここから消して CLAUDE.md・README・コードに反映する。未決事項は実装の中で決めるか、`docs/open-questions.md` に移す。

議論に使った図（利用者の仕事と algr の重なり、遷移の今と変えた後）：https://claude.ai/artifact/K9TiCRvm2TTZqzZWSzjrNy （持ち主だけが開ける）

## 背景

- 利用者の仕事の流れと algr の流れは部分一致する。algr が持つのは「何を作るか詰める」から「マージ」までで、その前（タスクに分ける）と後（リリース、運用）は外にある
- 人に上がった答えは必ず起票に戻り、1 つの問いで起票・実装・レビューが走り直す。dogfooding では 1 件あたり 8 本のジョブが走った（最短は 4 本）。人が推奨案をそのまま認めても一周する
- 自動マージは `done` にするだけで、実際にマージする口が無い
- マージのゲートや安全網の問いにメタプログラマーを答えさせていて、処理の層とメタの層が混ざっていた

## 決めたこと

### 1. 人の立場と 2 つの層

- **処理の層はクライアント。** タスクの問いには、要望したものを出してよいか（マージしてよいか、公開 IF を変えてよいか）も含めて、すべてクライアントが答える。
  ふだんの出番は「やりたいことをまとめ、タスクに分けて順番を決める」まで。そこから先は例外だけ `answer` する
- **メタの層はメタプログラマー。** タスクには答えない。クライアントの答えの記録、`algr stats`、report を見てルールを直す（`distill`、`proposals`、`accept`、`decline`）
- **立場を誰が埋めるか（人か、その横の AI か）は algr は区別しない。** `by: "human"` は「ルールではなく立場から来た」と読む。
  algr が保証するのは「フローの中では決めず、立場に渡す」まで。文書の「人のゲート」「人に上げる」「人に知らせる」は立場の言葉に直す
- **こだわり度は `new` の入力にしない。** 任せるルール（答えではなく「誰が決めるか」を指すルール。R006、R007 が例）で持つ。
  クライアントが `new` で出すのは、ルールが当たるかを読める事実（何を、何のために）
- **PJ メンバー（PR をレビュー・マージするチーム）は立場の外。** フローの外の手続きとして扱う

### 2. 判断待ちを役ごとの状態に分ける

- `needs-decision` を消し、`waiting-intake` / `waiting-implement` / `waiting-review` に分ける（名前は案）
- 起票・実装・レビューのどれも人に聞ける。聞く役は問いを結果に書いて終わる（返事を待たない）。
  答えが出たら聞いた役の状態に戻り、その役のジョブを要約から起動し直す。頭（起票）には戻さない
- レビューが聞いたときは、答えを持って起動し直したレビューが、承認か修正依頼かを決める。答えが判断どおりかを core は見比べない
- 実装とレビューも、聞く前に `input.rules` を当てる。当たらないものだけ聞く
- 戻り先はタスクの項目ではなく状態で持つ。状態ごとの滞在時間や通過回数が、そのまま役ごとに分かれる（R002、R003）
- CLI で判断待ちをまとめて拾えるようにする（例：`algr list --state waiting`）
- R008 により、旧形式の読み込みや移行は持たない

### 3. マージ

- `approved` 状態、`algr merge`、`flow.merge` を消す。マージの前に止めるのは、ルールか安全網に当たったときにレビューが `waiting-review` でクライアントに聞くこと。
  最初はルール「マージ前に必ずクライアントに聞く」で始め、メタプログラマーが記録を見て狭める
- 承認したらマージのアダプタに頼み、`merging` で待つ。マージ先に入ったと知ったら `done` にする
- **MergeAdapter**（新しいアダプタの種類、`[adapters.merge]`。名前は案）。実行アダプタと同じ組み立てにする
  - `request(task)`：マージを頼む。同じタスクで二度呼ばれても二重に頼まない
  - `status(task)`：`merged` / `open` / `changes`（PJ の指摘つき）/ `closed`
  - core は tick で `status` を見て、`merged` なら `done`、`changes` なら実装に戻す（指摘は `feedback` に）
  - TaskAdapter には入れない。タスク管理（issue、ボード）とコードの置き場（git、PR）は別のシステムになりうる。同じシステムなら 1 つのクラスで両方の IF を実装し、設定の 2 か所から指せばよい
  - フェイクはすぐ `merged` を返す
- **マージ先は利用者が設定で選ぶ。** core は同じで、アダプタの設定で決まる
  - A：マージ先は main。PJ が 1 件ずつレビューしてマージし、アダプタは PR の状態を見る。依存の鎖の 1 本ごとに PJ を待つので、タスクが大きくなりがち
  - C：マージ先は統合ブランチ。アダプタがすぐ git でマージし、PJ は統合ブランチの PR をまとめて見る。タスクを小さく保てる。dogfooding はすでにこの形
  - C では、統合 PR への PJ の指摘は新しいタスクとして起票する。どのタスクを 1 つの統合 PR にまとめるかは、クライアントがタスクに分けるときに決める（core はまとまりを持たない）
- 依存はマージ先に入ったとき（`done`）に解ける。起票は依存先を待たずに進める（今のまま）
- PJ メンバーの修正依頼の数は、algr のレビューが見逃した数としてメタプログラマーが見る（`algr stats` に出す）

### 4. 先に測ること（R012）

- 役ごとのジョブの本数とトークン数（走り直しがどれだけ減ったか）
- `ready` の滞在時間（依存の待ち）
- 人に上がった回数を判断待ちの状態ごとに（どこのルールが足りないか）

## 未決

- `reopen` をどちらの立場の操作にするか（失敗の原因はフロー側にあることが多い）
- `status` が `closed`（PJ がマージせずに閉じた）のときの状態。今の状態では `failed` が近い
- PJ の修正依頼を `flow.max_rework` に数えるか
- 状態とアダプタの名前
- C で統合 PR を出すのは誰か（クライアント側、algr の外が自然）。main を統合ブランチに取り込むのは誰か
- やめる操作（canceled）と、目的を後から変える操作を取り込むか
- `done` の後にクライアントが結果を見て違ったときの `new` から、元のタスクを指せるようにするか

## 進め方

1. **フローの作り直し**：2 と 3、それに 1 の文書の書き換え。`flow.py`（`TRANSITIONS` / `INVARIANTS` / `EVENT_DATA` / `STATE_HELP` / `EVENT_HELP`）、
   `engine.py`、`adapters/`（MergeAdapter とフェイク）、`config.py`、`cli.py`（`STANCES`、`merge` を消す、判断待ちをまとめて拾う）、`diagrams.py`、
   README の表、CLAUDE.md（人の立場、アダプタの数、状態）、`prompts/common.md`、テスト。遷移と表と図を同時に直すので 1 つにまとめる。algr には流さない（流れそのものを作り替えるため）
2. **プロンプト**（1 の後）：起票にコードを読ませ、実装で手が止まる点と安全網に当たる点を先に出させる。蒸留に任せるルールを提案させる。
   実装とレビューに「聞く前にルールを当てる」と聞き方を足す。起票 1 回あたりのトークンを測る
3. **指標**（1 の後）：人に上がった回数を判断待ちの状態ごとに出す。PJ の修正依頼の数を出す。README の `algr stats` の説明を直す
