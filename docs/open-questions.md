# 未決事項

フェーズ1に入る前に決めたいこと。重い順に並べ、それぞれに推奨案を付けている。
決めたら、ここから消して CLAUDE.md・README・コードに反映する。

## フローの形が変わるもの

### 同期の起票とジョブの関係
対話の起票を、BLOCKED のエージェントに attach して答えるのか、CLI で needs-decision を素早く往復するのかが決まっていない。
「後で決める」項目だけをキューに回すには、チャネルをタスク単位（`source` から決まる）ではなく未決事項ごとに持つ必要がある。

## IF に項目を足すもの

### 蒸留のタイミング
企画書の方針（同じ論点が 2 回たまったら提案、周期でまとめて 1 つの PR、レビュー予算内で影響の大きい順）はタスクをまたぐので、タスク単位のジョブに収まらない。今は人が答えるたびに即提案している。

推奨：タスクに属さない周期のジョブをコアに持たせ、起動の周期はトリガーで決める。

### トークン消費の設計
長く走る、やり取りの多いエージェントは文脈が膨らみ、消費が急に増える。設計の前提として次を置く。

- エージェントは役ごとの短いジョブにし、結果を返したら終わる。長いセッションを持ち回らない
- 引き継ぎは会話の履歴ではなく、タスクに書いた要約（未決事項、判断、PR）で行う。引き継ぎの費用は要約の大きさで決まる
- 人を待つ間にエージェントを起こしたままにしない。待つときはジョブを終え、答えが出たら要約から起動し直す（attach で待つのは例外にする）
- ジョブに渡すルールは適用範囲で絞る。今は `job_input` が全ルールを渡しているので、ルールが増えるほど全ジョブが重くなる
- 往復には回数の上限を付ける（レビュー ↔ 実装は `flow.max_rework` で済み。起票 ↔ 人が残る）
- 実行アダプタが結果と一緒に使ったトークン数を返し、タスクあたりのトークン数を指標に足す
- 役ごとにモデルと上限を設定で選べるようにする（起票・レビュー・蒸留は軽いモデルでもよい）。プロンプトとルールは共通部分を先頭に置き、キャッシュを効かせる

### フェーズ1の完了条件
差し戻し率の傾向を見るには指標が要るが、指標はフェーズ2にある。

推奨：差し戻し率だけを `.algr/state/events.jsonl` から集計する機能をフェーズ1に入れる。

### ルールの適用範囲
「範囲外なら人に上げる」には範囲が要るが、`Rule` は ID と本文しか持たない。範囲を k2down と algr のどちらで持つか、いつ入れるかを決める。
